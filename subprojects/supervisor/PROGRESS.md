# Advisory progress controller

This standalone, original implementation evaluates trusted `Contract` facts using `assess(contract, previous=None)`. It does not parse prose, call a model, block, continue or execute. The application supplies explicit unit criteria (unit ID, artifact, current revision, check and environment), external receipt IDs/results, revoked IDs, target count, permission and stop/budget facts, pending callbacks, and a finite no-progress attempt count and limit. Identity authentication, receipt provenance, current artifact revisions and environment, callback status and attempt accounting are the caller's responsibility.

A unit counts only if a non-revoked passing receipt exactly matches its current criterion and no non-revoked fail or unknown receipt conflicts. Repeating a receipt or adding another pass for the same criterion does not increase unit count. A reused receipt ID with different contents is rejected. Revocation or a change to revision, check or environment can remove acceptance. A receipt from another environment cannot satisfy a criterion. `new_units` compares accepted criteria with the previous advisory result; prose and repeated submissions are not inputs. A changed requirement is not itself evidence of completion; a matching valid receipt is still required. The first observation reports all accepted units as new relative to an empty baseline. A caller must retain the right prior state and count attempts; this module does not persist or advance counters.

`completion` is independent of `stop_reason`: explicit user stop, budget exhaustion, permission states and scope cancellation take priority; then a satisfied target, waiting callback, attempt limit or remaining work is reported. A pending callback is not a quit. These reasons describe supplied facts and are not authorization to intervene. Invalid or uncertain input needs handling by the calling application; it is not automatically interpreted.

This does not modify Supervisor's existing `Snapshot` or policy. A future adapter may translate authenticated matching receipts and acceptance criteria into these types and use the result as context, while preserving the policy's separate authority, feasibility and coverage checks. No live integration, artifact recheck, or behavior claim has been validated.

The roadmap draws conceptually on lifecycle and no-progress patterns described by [protoAgent](https://github.com/protoLabsAI/protoAgent) (MIT, copyright 2026 protoLabs); this implementation does not copy that framework.
