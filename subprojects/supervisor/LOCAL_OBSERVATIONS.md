# Scoped local artifact observation prototype

`local_observations.check_and_record` is a trusted-application entry point. It takes a scoped ledger, criterion ID, expected ledger version, host fresh-scope attestation, and a trusted registry of roots, operation definitions and environments. It reparses the actual captured contract, resolves the criterion, invokes the actual local checker, checks registry and root device/inode before and after, and transactionally records the checker result in a separate scoped table while incrementing the ledger version. The checker generates the observation ID. This API never accepts a caller-supplied status, hash, observation ID or source role. A private internal SQLite sink exists to persist and replay already-created records; it is not a security boundary against code or a local process with database access.

The canonical original includes origin `local_artifact_checker/v2`, scope, contract source event ID, criterion, environment, root ID, root device/inode, registry digest, checker status/hash/time and checker-generated ID. Version 2 also records the ordered captured-event IDs and ledger version present before the check; the recording transaction rejects intervening events. Only coordinator-validated records in the reserved `local-observation:` namespace carry that provenance. The canonical root path is stored separately in the private database, while the model-visible evidence contains the registry digest and root identity rather than the path. Observation IDs are unique across the ledger; identical internal replay is idempotent at the current version, changed reuse conflicts, and stale CAS writes fail. The table is created on writable open; old v1 observation records are not silently promoted to v2 provenance and cause conservative abstention. Fresh pilot launches use new private databases. All scoped observations—including missing, mismatch and unverifiable—are retained and count toward the bounded evidence budget.

Coordinator source IDs reserve the `local-observation:` namespace and reject native aliases that use it. Each observation is reconstructed as tool-like evidence from its immutable canonical record, never a user source. Obligation and permission sources still require captured user prompts. A policy receipt citing an observation must match its criterion path, expected SHA-256 revision, check, environment and checker result. Coordinator requires the current trusted registry and matching root descriptor; it includes every scoped observation or abstains. Before saving a confirmed claim it rechecks the registry, root and file result, then performs the ledger version CAS. Contradictory earlier observations are not discarded; their inclusion may prevent a claim. No capture gap, including Stop identity gaps, is removed by this extension.

This is not protection against malicious local code or a model that can modify the trusted application, registry, database, root or underlying filesystem. The application must independently authenticate its caller, root registry, environment, fresh-scope attestation, source roles and action description. Device/inode checks before and after do not make the filesystem and SQLite one atomic transaction: a file, root, permission, host reply or registry can change after recheck or be swapped and restored between checks. A future action boundary must verify external currency and authorization again. No operation, live hook or native model call is implemented here.

The trusted host must select the root appropriate to the task and criterion. Policy `Acceptance` has no root ID: matching environment, relative path, check and expected hash do not authorize reusing an observation from a different root. This prototype does not itself bind a selected policy action to one root; the integration must enforce that scope before relying on an observation.

Historical observations are retained and all are rechecked before a claim. If the artifact changes, earlier missing, mismatch or match observations may no longer agree with the current file, so the coordinator can continue to abstain even when a later observation matches. There is no latest-wins rule or supersession model. A future explicit revision model must define how old observations are scoped or retired; do not silently discard negative evidence.
